# Saved playlists and logins

Version 0.9.0 saves multiple M3U file/URL or Xtream playlists, root catalogues and classified movie/episode positions on this device. One playlist is active at a time. Opening the app or switching playlists restores the selected catalogue cache without automatically refreshing it or starting playback. Artwork may load through the existing image loader as you browse. Source management is in Settings; HTTP operations proceed without repeated approval. See [browsing, search and favourites](library-browsing.md) and [Continue Watching](continue-watching.md). The app supplies no channels or subscriptions.

## Using it

- Import a file or URL, or enter your Xtream login. A saved timestamp appears after the library is committed; adding a playlist preserves the others.
- Open **Playlists** to select a cached playlist, rename it, or remove a particular playlist. File/URL imports start with a localized type and number; Xtream starts with the supplied playlist name. Friendly names are encrypted and never derived from URLs or credentials.
- **Refresh playlist** reloads a saved URL/server source. For a file, choose the document again; the app keeps its parsed catalogue without retaining document access.
- **Remove playlist** confirms the named playlist, then removes only that playlist's catalogue and protected login. Removing the active playlist selects the oldest remaining playlist; removing the last returns to empty setup. Cancelling the confirmation changes nothing.
- Failed refresh/import keeps the working library. Download/parsing can be cancelled. During the final local save the app shows Saving and completes the atomic commit before another operation.
- If protected data is unreadable, imports into that state are blocked. Use Playlists to select another cached playlist or explicitly remove the damaged one. A failed switch preserves the working source. The app does not silently reset the database or invent a new key for existing ciphertext.

Switching closes playback on success and selects the cached root catalogue. Opening a series fetches its episode list with that playlist's restored login. Watched episodes also have a protected snapshot for direct Continue Watching; this is not an offline copy of every episode list or of the video. Root favourites, selected-source search and playback positions are local to each playlist. Combined catalogues, source editing/reordering, full episode-list caching, EPG and scheduled refresh remain open.

## Protection and schema

`core:storage` uses Room 2.8.5, KSP 2.3.6 and exported schema version 4. Manual 1-to-2, 2-to-3 and 3-to-4 migrations preserve source/item IDs, envelopes, locator ciphertext, generation IDs and the existing Keystore alias; there is no destructive fallback. Earlier schemas remain exported for migration fixtures. Schema 3 added encrypted artwork, optional metadata, FTS4 search and source/item favourites. Schema 4 adds the independent watch-progress table and its recent-history index without rewriting existing source/catalogue data.

Credentials/source URLs, friendly playlist names and every playback locator are encrypted BLOBs. A random per-source data key uses standard AES-256-GCM per row; Android Keystore wraps it and the source configuration. Catalogue locators bind to source/generation/item associated data. Watched episode snapshots bind to the source and authenticated stable media reference independently of catalogue generation, so refresh can preserve them. Catalogue labels/categories and progress timing/completion remain in app-private database columns. Targeted deletion removes that playlist's catalogue, favourites and progress, retaining the shared wrapping key while any saved source remains. After committed last-source deletion, orphan-key cleanup is best effort; a fresh import into an empty database retries cleanup before creating its new envelope. Existing backup/device-transfer exclusions cover the database; reinstalling requires adding sources again. This does not claim protection from a compromised running app or forensic secure deletion of all filesystem history.

Refresh carries the explicit playlist ID and preserves local item IDs for matched provider kind/IDs or exact private M3U locator/occurrence keys. Duplicate entries and separate imports of the same connection stay distinct. Favourites and progress follow only confidently matched identities; missing history stays unavailable rather than attaching to another title. Catalogue replacement and active selection are transactional, separate from identity mappings and other playlists. No raw provider addresses, credentials, bodies or exception causes enter logs/telemetry.

## Verification workflow

JVM tests cover source encoding/redaction/bounds, names, authenticated encryption, directory-aware cached switching without network, failed activation retention, targeted rename/removal, HTTP consent, file refresh and local commit/cancel behavior. Android fixtures cover actual schema-1 encrypted migration, independent source catalogues, protected names, explicit refresh targets, last-key cleanup failure/retry, Room/Keystore reopen, transaction rollback, missing keys and tampered addresses, identity preservation and bilingual phone/TV management. Fixture implementation is not a substitute for actual latest-head device results.

CI's [device wrapper](../../scripts/device-tests.sh) runs instrumentation, then a [separate-process probe](../../scripts/persistence-process-test.sh). On its disposable emulator it reinstalls test APKs after Gradle cleanup, seeds two synthetic playlists and a renamed label, force-stops the app, verifies the directory, active selection and both cached roots with a different PID, then clears the fixtures. Explicit exit propagation and stubbed shell tests prevent timeout/ADB/probe failures from being masked. These scripts can replace app data: do not run them on the owner's interactive emulator without an agreed testing window.

See [progress](../../progress.md) and the delivery PR for actual latest-head results. All fixtures are synthetic. Local testing uses one disposable review emulator at a time and preserves the owner's interactive source/session. The earlier unexpected laptop shutdown remains unexplained; no host firewall, virtualization driver or reboot changes are part of this workflow.
